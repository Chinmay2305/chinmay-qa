PROJECTTaskFlow (demo)
VERSION1.6
MAINTAINED BYQA
STATUSActive

1. Overview

TaskFlow (demo app) is a web application for creating, organising and completing personal tasks. This document is the single source of truth for QA: how the product works, how it is tested, and what is currently at risk.

Scope of release 1.6
  • Task create, edit, delete, complete
  • Filters by status and priority
  • Email-based password reset
  • Admin user management
Stack

React front end, REST API, PostgreSQL database, hosted on cloud staging and production.

2. Roles & permissions

Access is role-based. Every test scenario states the role it runs under.

  • Guest: view landing page, sign up, log in
  • User: full control of own tasks only; cannot see other users' data
  • Admin: all User rights, plus view, disable and delete user accounts
Verification points
  • A User opening an Admin URL gets a 403 page
  • A disabled account cannot log in and sees a clear message

3. Modules & flows

M1 · Authentication
  1. Open Sign up and submit name, email, password
  2. Verify account is created and user lands on the dashboard
  3. Log out and log in with the same credentials
M2 · Tasks
  1. Create a task with title, priority and due date
  2. Edit, mark complete, then delete it
  3. Confirm the record count updates on the dashboard
M3 · Filters & search

Status and priority filters combine with AND logic. Search matches task titles only.

4. Business rules

Rules the product must enforce. Test cases reference these IDs.

  • BR-01 Password: minimum 8 characters, at least one number
  • BR-02 Task title: required, maximum 100 characters
  • BR-03 Due date cannot be earlier than today
  • BR-04 Five failed logins lock the account for 15 minutes
  • BR-05 Deleted tasks are soft-deleted and kept for 30 days

5. Environments & data

  • QA: latest build, reset nightly, used for daily testing
  • Staging: release candidate, production-like data, used for regression and sign-off
  • Production: read-only checks after release
Test accounts
  • One account per role (Guest needs none)
  • Credentials are kept in the team vault, never in this document
Data reset

QA data resets at 02:00. Re-seed script and seed data are version-controlled.

6. Integrations & APIs

Key endpoints
  • POST /auth/login · returns token and role
  • GET /tasks?status=&priority= · list own tasks
  • POST /tasks · create, validates BR-02 and BR-03
  • DELETE /tasks/:id · soft delete per BR-05
External services

Email provider for password reset. Sandbox mode is used on QA, so no real emails are sent.

7. Test strategy

In scope
  • Functional, regression, cross-browser (Chrome, Firefox, Edge) and API testing
  • Automated regression of the core flows in M1 and M2
Out of scope
  • Load testing of production
  • Third-party email delivery
Entry and exit criteria
  • Entry: build deployed to QA, smoke test passed
  • Exit: no open Critical or High defects, all planned regression tests passed

8. Risks & issues

  • High · Authentication and role checks: security impact. Mitigation: automated permission tests every build
  • Medium · Filter combinations: many untested paths. Mitigation: pairwise test design
  • Low · Date handling across time zones. Mitigation: boundary tests
Open defects
  • BUG-001 · Weak password accepted on sign up (High)
  • BUG-003 · Duplicate entry on double-click (Low, awaiting retest)

9. Revision history

Updated by QA after every sprint and release.

  • v1.6 · Added BR-05 and soft-delete API behaviour
  • v1.5 · Added Admin permissions and account lock rule
  • v1.2 · Added environments, data reset and test strategy
  • v1.0 · Initial version: overview, roles, core flows
